# Mock corpus (`data/traces/`) — what it is and how to regenerate

Synthetic LLM-observability traffic for demoing the Nightshift batch job. Three days,
three simulated agent products, six planted failure modes at known proportions, plus a
ground-truth key so the demo can show that clustering **recovered** the planted modes
rather than merely produced a plausible-looking taxonomy.

Everything here is generated by `tools/mockgen.py`. Nothing was hand-written line by line, and
no file under `nightshift/` was modified.

## Regenerate

```bash
python3 tools/mockgen.py            # rewrite the 3 day files + data/ground_truth.json
python3 tools/mockgen.py --stats    # print the breakdown, write nothing
```

Seeded with `SEED = 20260826`, so the output is byte-for-byte reproducible. Re-running
overwrites the three day files in place; `data/traces/2026-08-26.jsonl` (real capture) is
left alone.

Verify it parses:

```bash
python3 -c "from nightshift import episodes; e=episodes.from_proxy('2026-08-25'); \
           print(len(e)); print(e[0]['transcript'][:300])"
```

## Volume

**1052 records** across three days, one JSON object per line, in `data/traces/<day>.jsonl`.

| day | weekday | records | support | coding | rag |
|---|---|---:|---:|---:|---:|
| `2026-08-23` | Sunday | 172 | 73 | 57 | 42 |
| `2026-08-24` | Monday | 431 | 172 | 149 | 110 |
| `2026-08-25` | Tuesday | 449 | 182 | 139 | 128 |
| **total** | | **1052** | **427** | **345** | **280** |

Sunday is deliberately light. Within each day, timestamps are drawn from a business-hours
curve (UTC) peaking 10:00-16:00 with a thin overnight tail, and each file is written in
timestamp order the way a real append-only log would be.

## Products

`episodes.from_proxy()` sets `episode["project"]` from the record's `model` field, and
`report.py` buckets "worst projects" by that. Each product therefore gets its own gateway
deployment alias as the model name (LiteLLM/Azure style); the real upstream model id is
echoed in `response.model`.

| product | deployment alias (= `project`) | upstream model | records | failures | rate |
|---|---|---|---:|---:|---:|
| customer-support agent | `support-agent-gpt-4o-mini` | `gpt-4o-mini-2024-07-18` | 427 | 154 | 36.1% |
| coding assistant | `code-assistant-gpt-4o` | `gpt-4o-2024-11-20` | 345 | 95 | 27.5% |
| RAG research assistant | `rag-research-gpt-4o-mini` | `gpt-4o-mini-2024-07-18` | 280 | 120 | 42.9% |

The RAG assistant is the deliberately worst performer, so "worst projects" has a clear
winner instead of three indistinguishable bars.

- **customer-support agent** — refunds, shipping, address changes, duplicate charges,
  damaged goods, locked accounts, membership cancellation. Each user turn carries an
  account-context block and a short policy excerpt.
- **coding assistant** — flaky tests, null derefs, N+1 queries, refactors, test writing,
  online migrations, worker races, dependency upgrades. Each user turn carries the code
  context it is allowed to know about.
- **RAG research assistant** — nine internal-doc topics (privacy SLAs, on-call escalation,
  vendor review, parental leave, expenses, model deprecation, incident severity,
  encryption at rest, contractor classification). Each user turn carries the retrieved
  passages with their ids.

## Failure modes

**369 of 1052 records (35.1%) carry a planted failure**; the other
683 (64.9%) are genuinely good responses.

| planted mode | what it looks like | count | % of corpus | % of failures |
|---|---|---:|---:|---:|
| `ignored_constraint` | user states an explicit constraint in their turn; the answer does the opposite | 89 | 8.5% | 24.1% |
| `hallucinated_source` | cites a policy section, help-centre URL, repo file or passage id that was never provided | 98 | 9.3% | 26.6% |
| `tool_loop` | repeats an identical tool call with identical arguments after it has already failed 3-5 times | 41 | 3.9% | 11.1% |
| `unsafe_advice` | states medical, legal, financial or compliance conclusions with certainty it has not earned | 44 | 4.2% | 11.9% |
| `truncated` | stops mid-sentence part-way through the task, `finish_reason: "length"` | 45 | 4.3% | 12.2% |
| `wrong_question` | answers a different, adjacent question than the one asked | 52 | 4.9% | 14.1% |
| `none` | genuinely good response | 683 | 64.9% | — |

**Failure modes are never named in the text.** No record contains the string "hallucinated",
"tool loop", "ignored constraint", "truncated" or any other mode label — a judge has to
infer the failure from reading the exchange. That is the whole point: if the label were in
the text, recovering it would prove nothing.

## Ground truth

`data/ground_truth.json` is a flat mapping from a stable record key to the planted mode:

```json
{ "2026-08-25#0": "none",
  "2026-08-25#1": "hallucinated_source",
  "2026-08-25#2": "none" }
```

The key is `"<day>#<line_index>"`, where `line_index` is the 0-based line number in
`data/traces/<day>.jsonl`. That is exactly the index `episodes.from_proxy()` uses when it
builds `episode["id"]`, so:

```
ground-truth key   2026-08-25#41
episode id         proxy/2026-08-25#41
```

To score a batch run, strip the `proxy/` prefix off `episode["id"]` and look the key up.
All 1052 keys are present; every episode has exactly one.

## Record shape

Exactly what `nightshift/store.py` writes and `nightshift/episodes.py:from_proxy()` reads:
`kind`, `ts`, `path`, `status`, `model`, `latency_s`, `streamed`, `request`, `response`,
`usage`. Two details the generator is careful about, because `from_proxy()` builds the
judged transcript from **only** the last user message plus `choices[0].message.content`:

- All the evidence a judge needs — retrieved passages, code context, the tool scratchpad,
  the user's explicit constraint — lives in the **final user turn**, never only in the
  system prompt, which the judge never sees.
- Multi-turn history (prior turns, tool observations) is present in `request.messages` for
  realistic `n_turns` and prompt-token counts, but the loop is always *also* legible from
  the final turn alone.

### Numeric realism

- `prompt_tokens` and `completion_tokens` are derived from actual content length
  (~3.9 chars/token). Median prompt 229, median completion 134.
- `latency_s` is correlated with `completion_tokens` (r = 0.51):
  ~0.016 s/token plus overhead, with a 3.5% slow tail for upstream queueing. Median
  2.55s, p95 4.61s, max 22.72s.
- `total_tokens == prompt_tokens + completion_tokens` on every record, and the top-level
  `usage` matches `response.usage`.
- `finish_reason` is `"length"` on exactly the 45 truncated records and `"stop"` on all
  others; those records also carry a matching `max_tokens` and a completion count that
  lands on the cap.
- 13% of calls are marked `streamed`; all are `status: 200` (this corpus is about answer
  quality, not transport failures).

## Validation story

The demo runs the batch job over these three days, lets the judge label each episode and
the clusterer group the labels, then compares the recovered taxonomy against
`ground_truth.json`. Six modes went in at known proportions; the question the demo answers
is how many of them come back out, and whether the per-project ranking recovers the RAG
assistant as the worst performer.
